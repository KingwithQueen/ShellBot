# Windows 1.0.4 数据容量

Windows 版提高了源码、文件、图像、文档及任务输入输出容量。`host_capabilities` 返回当前后端的实际值，`tools/list` 使用相同上限。这里的 MiB/GiB 按 1024 计算；文本容量按 UTF-8 字节计算，不是字符数。

## 传输源码与长命令

先用 `fs_write` 创建脚本，再通过 `task_start` 启动解释器并把脚本路径作为一个参数。已有文件的覆盖/修改继续要求原摘要及私有备份。超过 8 MiB 的源码或二进制用 `artifact_upload` 分块创建，再执行该文件；上传不能覆盖现有文件。程序支持从 stdin 读脚本或数据时，也可分次调用 `task_input`，最后发送 EOF。

Windows 的 [CreateProcessW](https://learn.microsoft.com/zh-cn/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw) 最多容纳 32767 个 UTF-16 单元，包含末尾 NUL。因此程序名、空格、引号及转义后的完整命令最多为 32766 个单元。本版精确计算转义后的长度，取消先前按约两倍原始长度预估的提前拒绝。[cmd.exe](https://learn.microsoft.com/en-us/troubleshoot/windows-client/shell-experience/command-line-string-limitation) 本身还有 8191 字符限制；应采用脚本文件或标准输入传源码。

网络不稳定时减小 `max_bytes`。下载按 `next_offset` 继续，可重试相同的最近一块；上传保留原 `transfer_id`、偏移和字节重试，完整大小与 SHA-256 校验通过后才创建文件。`max_chunk_bytes` 是上限，`default_chunk_bytes` 是省略参数时的值。重启不恢复暂存传输，连接断开不等于传输实例已消失，可先查 `status`。

## 保留容量的原因

请求和响应必须能在内存中解析；Base64 会增加约三分之一体积，文本嵌套 JSON 还会再次转义。解码像素数、Office 展开量、标准输入队列及每任务输出限制用于控制内存和磁盘增长。新建项目默认工作进程内存配额为 1024 MiB；已显式配置的较低配额保持有效，最大文件容量不代表任意并发组合都能装入配额。

审批、身份、读取范围、摘要核对和备份规则继续有效。大请求进入 worker 和读取 HTTP 正文的等待窗口提高到 120 秒，但这不是可中断的磁盘 I/O 硬超时。桌面直接逐键输入仍限 512 个 UTF-16 单元，保持人工暂停和控制反馈及时；长文本使用剪贴板、文件或标准输入。

配置文件和本地管理指令保留各自的小容量；审批/任务记录、备份槽、日志保留、超时和执行隔离属于资源及权限控制。所有者检查及持久历史对较大正文显示前 64 KiB 预览、完整长度和既有操作摘要，并明确标注截断；历史不持久复制图像或产物 Base64，完整审批和幂等回执在当前实例内保留。预览不能当作完整源码备份。

本轮先验证 Windows。POSIX 后端保留原有数据容量；Mac/Linux 的重新移植与原生验收另行进行。客户端、网关或外部服务还可能设置自己的限制，Windows 本机回归不能证明外部链路也接受相同大小。
