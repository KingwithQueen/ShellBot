# Linux / macOS media and artifact tools

The x86_64 Linux and macOS backends implement the existing project-scoped MCP tools:

- `artifact_download`: open an authorized file up to 64 MiB, read sequential Base64 chunks up to 32768 bytes, inspect status or cancel.
- `artifact_upload`: open a create-only destination with size and SHA-256, write sequential chunks, then commit after complete hash verification. Existing destinations are never overwritten. Uploading requires a writable file scope.
- `image_view`: fully decode a single PNG or JPEG (16 MiB input, 16,777,216 pixels), preserve the validated original when possible, or return a bounded PNG derivative. Alpha is preserved and resizing uses premultiplied interpolation. EXIF orientation is not applied.
- `document_info`, `document_read`, `document_preview`: PDF pages, DOCX document text, XLSX worksheets and PPTX slides. PDF preview renders the page. Office preview is structured text, not original layout. Spreadsheet formulas return stored values and are never recalculated. No OCR, legacy DOC/XLS/PPT, macro-enabled or password-protected document support.

Use `config/posix-media.example.json` as a registry template. Set absolute workspace and private data paths. Approval mode defaults to `always`; native management and owner commands can inspect and approve the exact request. Transfers are bound to caller, project, backend instance and current policy. IDs expire (default 300 seconds, maximum 900). Only the most recent chunk may be retried. Request keys provide open/commit idempotency. No anonymous download URL, external client attachment integration or restart resume is provided.

Uploads use a private unlinked 0600 spool, removed by the OS on close/crash. Target creation uses anchored directory descriptors and exclusive creation; symbolic links, special files, hard-linked sources and existing destinations are rejected. Download descriptors and file versions are checked before and after reads; POSIX cannot prohibit other applications from editing a source. A changed source fails the transfer. Do not describe this as a filesystem snapshot or mandatory write lock.

Document sources stay in memory and are never edited. Input is limited to 32 MiB; extraction is limited to 1 MiB per unit with UTF-8 paging. PDFs have at most 4096 pages. Office supports 256 units, 2048 ZIP entries, 8 MiB per entry, 64 MiB total expansion, depth 64 and one million XML events per part. ZIP64/encryption, duplicate entries, DTDs/custom entities and macros are rejected. OOXML relationships determine document/sheet/slide order. External relationship targets are not fetched. Shared strings, inline strings and stored spreadsheet values are supported. Deleted Word text and spreadsheet phonetic annotations are skipped.

PDFium 157.0.8086.0 (without V8/XFA) is vendored separately for Linux/macOS x86_64, with publisher archive digests and library hashes in `third_party/pdfium/*-x64/PROVENANCE.json`. CMake verifies the library and copies it beside the executable, including inside the Mac app bundle. The backend uses only that absolute path, verifies its SHA-256, rejects symlinks/multiple hard links and pins its descriptor. These checks do not sandbox the decoder or protect against a malicious process with the same uid. Office uses system Expat, ZIP deflate uses system zlib, image decoding uses the pinned stb_image header (PNG/JPEG only). Linux text preview uses Pango/Cairo and Fontconfig; Mac uses CoreText. No Office installation, converter subprocess or display server is required for media tools.

Build with the normal `scripts/build-posix.ps1 -Configuration Release -WithTests`. Runtime dependencies include Expat/zlib, Linux Pango/Cairo and the libraries documented in POSIX_REMOTE_DESKTOP.md. Install with `cmake --install`; distribute the adjacent PDFium library and all supplied notices. Do not remove the library when relocating a standalone executable. Apple Silicon is not yet supported by this pinned x86_64 runtime.

Automated fixtures exercise transfers, document extraction/rendering, image resizing and rejection boundaries over the actual native protocol. Physical UI, real external client attachments and visual fidelity on user documents remain manual acceptance; they are not inferred from automated checks.
